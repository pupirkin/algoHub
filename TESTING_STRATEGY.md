# AlgoHub — стратегия тестирования и качества

Версия 1.0 · 2026-11-12. Дополняет `ARCHITECTURE_PLAN.md`. Главный принцип: **статус продукта меняет не человек и не агент, а скрипт `pnpm dod <ID>`**, который проверяет, что всё перечисленное здесь существует и зелёное.

## 2. Тестирование алгоритмов — отдельный обязательный слой

Каждый алгоритм в `python/algorithms/` или `web/src/algo/` обязан иметь четыре вида тестов. Это не рекомендация: `pnpm dod` ищет файлы `test_*_oracle`, `test_*_props`, `test_*_golden`, `test_*_budget`.

### 2.1 Oracle (brute force на малых входах)
Для n ≤ 6–8 перебираем все варианты и сравниваем с оптимизированной реализацией.
- Social choice (P15): перебор всех попарных дуэлей → Condorcet; сумма Борда вручную; IRV пошагово.
- Balanced partition (P17): перебор всех разбиений на k команд, минимальная разница сумм рейтингов.
- Debt simplification (P07): проверка, что число переводов ≤ n−1 и что никакой перебор меньшего числа переводов не закрывает балансы (для n ≤ 6).
- CP-SAT (P31): на 3–4 сотрудниках и 5–6 сменах перебор назначений и сравнение значения целевой функции.
- Routing (P01, P02): перебор перестановок для ≤ 7 точек.

### 2.2 Property-based (инварианты)
Пишутся как **свойства предметной области**, а не «не падает»:
- Борда: монотонность (поднять X в одном бюллетене не ухудшает X); нейтральность к перестановке меток; детерминизм при одном seed.
- IRV: победитель получает > 50 % в финальном раунде; Condorcet-победитель, если есть, объявляется при `method=condorcet_first`.
- FairSplit: сохранение потока (сумма входящих = сумма исходящих для каждого), никто не платит больше своего долга, нет переводов A→B и B→A одновременно.
- FairTeams: размеры команд отличаются ≤ 1; ограничения «вместе/врозь» никогда не нарушены; при идентичных игроках разброс = 0.
- ShiftFair: ни одно жёсткое ограничение не нарушено в любом `FEASIBLE/OPTIMAL` ответе; при увеличении таймаута целевая функция не ухудшается; при пустом множестве мягких ограничений любое покрытие допустимо.
- Minimax meeting (P01): результат не хуже любого из кандидатов по минимаксу (проверка post-hoc на той же матрице).
Стратегии генерации — в `tests/strategies.py` / `tests/arbitraries.ts`, переиспользуются продуктами.

### 2.3 Golden-сценарии как спецификация
`products/<id>/scenarios/*.json`:
```json
{ "name": "three_friends_pizza_tie", "profile": "ROOM",
  "input": { "options": ["Pizza","Sushi","Burgers"], "ballots": [[0,1,2],[1,0,2],[2,1,0]] },
  "expected": { "method": "borda", "winner": null, "tie": ["Pizza","Sushi"], "explain_contains": ["pairwise"] },
  "ui": { "steps": ["create_room","join:Ann","vote:Ann:[0,1,2]", "…", "close", "assert_result"] } }
```
Один файл питает три теста: unit алгоритма (`input→expected`), контрактный тест API (сценарий через HTTP), Playwright (`ui.steps` исполняет generic-раннер `tools/scenario-runner`). Любой найденный баг сначала становится сценарием.

### 2.4 Бюджеты
- Солверы: `timeout_s` из настроек; тест проверяет, что при таймауте возвращается лучшее найденное решение со статусом `FEASIBLE`, а не исключение; `pytest-benchmark` фиксирует p95 на эталонных инстансах (small/medium/large) и падает при регрессии > 30 %.
- CLIENT-алгоритмы: бюджет 50 мс на эталонном входе в Vitest (`performance.now()`), чтобы UI не замирал.
- Детерминизм: один и тот же вход + seed → байт-в-байт одинаковый результат (включая порядок в объяснениях).

### 2.5 Невыполнимость и вырожденные входы
Обязательные кейсы: пустой вход; один участник/вариант; все одинаковые; противоречивые ограничения (ожидаем структурированное объяснение, не 500); NaN/отрицательные/переполнение; дубликаты; unicode в метках.

## 3. API и контракты

- **Снапшот OpenAPI** `services/algo-api/openapi.json` закоммичен. Тест генерирует актуальный и сравнивает; в CI дополнительно регенерируется `packages/api-client` и проверяется `git diff --exit-code`. Изменение контракта = осознанный коммит снапшота.
- **Версионирование:** префикс `/api/v1/<pid>`. Ломающее изменение → `/v2` рядом, `v1` живёт до удаления по ADR. Контрактный тест для каждой версии.
- **schemathesis** гоняет fuzz по снапшоту против поднятого API: 4xx допустимы, 5xx — падение.
- Обязательные тесты каждого эндпоинта: валидация (422 с понятными полями), authz (чужой/отсутствующий токен → 401/403, не 404-утечка), пагинация (где есть списки), лимиты размера тела, rate limit (429 после N запросов в тесте с заниженным лимитом), идемпотентность для `PUT /ballot` и `idempotency_key` у jobs.
- **Внешние провайдеры (DATA):** интерфейс адаптера тестируется contract-тестом, который гоняется и против `DemoProvider`, и (по флагу, с ключом из env) против реального — одинаковые assertions. Ошибки провайдера (таймаут, 429, мусор в ответе) эмулируются `respx`; ожидаем деградацию до `demo`/ошибки с Provenance, а не 500.

## 4. Данные и миграции

- Alembic на продукт, `version_table_schema=<pid>`. Тест: `upgrade head → downgrade base → upgrade head` на чистой БД.
- Запрет cross-schema FK проверяется тестом по `information_schema`.
- Фикстуры: `polyfactory`/`faker` с фиксированным seed; **никаких реальных персональных данных**, в том числе в сценариях и демо-режиме (имена из словаря, координаты — публичные достопримечательности).
- Retention: тест, что очистка удаляет просроченное и не трогает актуальное.

## 5. UI, e2e, доступность

- Один Playwright-тест на продукт = happy path из `scenarios/*.json` c `ui.steps` (+ 1–2 негативных: истёкший токен, закрытая комната).
- На каждом экране happy path: `axe` без нарушений уровня serious/critical; проход с клавиатуры (Tab-порядок, Enter/Space на контролах, Escape закрывает модалки); фокус возвращается после модалок.
- Мобильный viewport (375×812) и десктоп — оба в e2e-матрице.
- Пустое/loading/error состояния покрыты компонентными тестами (не e2e).
- Визуальные снапшоты — **не вводим** на этом этапе (шум при активной разработке дизайн-системы). Вернуться после стабилизации `@algohub/ui`.

## 6. Безопасность и приватность

- `gitleaks` в pre-commit; CI падает при секрете. `.env.example` — часть DoD.
- Тест: клиентский бандл портала не содержит значений серверных env (сборка + grep по известным именам переменных из `Settings`).
- Security headers проверяются e2e (`response.headers()` на главной): CSP, HSTS, X-Content-Type-Options, Referrer-Policy.
- Логи: тест, что `structlog`-процессор редактирует поля из списка (`email`, `display_name`, `lat/lng`, токены).
- Для ROOM/DATA: тест, что публичный `GET /rooms/{id}` не возвращает токены, хеши, чужие бюллетени до закрытия, точные координаты участников.

## 7. Определение готовности — `pnpm dod <ID>`

Скрипт (`tools/dod/`) проверяет и печатает таблицу ✅/❌. Статус в `registry.ts` нельзя поднять выше того, что разрешает DoD (lint-правило сверяет).

| Статус | Что требуется |
|---|---|
| `DESIGNED` | `docs/README.md`, `docs/PRD.md`, `docs/ARCHITECTURE.md`, минимум 3 сценария в `scenarios/`, запись в `registry.ts` |
| `IN_PROGRESS` | ветка/PR существует, `docs/STATUS.md` с датой ≤ 14 дней |
| `MVP_READY` | все уровни §1 зелёные для пакета; 4 вида алгоритмических тестов (§2); OpenAPI-снапшот актуален (если есть api); Playwright happy path зелёный против compose; axe чисто; `docs/VALIDATION.md` с измеримой гипотезой; `.env.example` обновлён; `CHANGELOG.md` запись |
| `VALIDATING` | аналитические события продукта видны в Umami; включён флаг; известные баги перечислены |
| `LIVE` | деплой выполнен (см. DEVOPS), smoke-тест пройден и записан в `STATUS.md` с датой и URL |

Агент **не имеет права** писать `MVP_READY`/`LIVE` вручную — только после зелёного `dod`. Если инструмент недоступен в среде (например, нет Docker), DoD печатает `NOT RUN` для соответствующих пунктов, и статус остаётся прежним.

## 8. CI-политика

- На PR: статика + unit + property (быстрый профиль) + контракты + интеграция для **затронутых** пакетов (`turbo run test --filter=...[origin/main]`; для Python — path-filter по `products/<id>/api`, `python/**`, `services/**`); e2e — для продуктов, чьи файлы затронуты, плюс smoke портала всегда.
- Ночью (`schedule`): полный прогон, property ×20, `schemathesis` долгий профиль, benchmarks, `pip-audit`/`pnpm audit`.
- Флейки: тест помечается `@flaky`/`pytest.mark.flaky` **только** с ссылкой на issue и сроком; ретраи не включаются глобально. Больше 3 флейков в продукте — блок `MVP_READY`.
- Обязательные проверки для merge в `main`: `lint`, `typecheck`, `test`, `contract`, `e2e-smoke`.

## 9. Что тестировать в продуктах каждого профиля (шпаргалка для генератора)

| Профиль | Обязательно сверх базового |
|---|---|
| CLIENT | бюджет 50 мс; url-state round-trip (encode→decode идентичен); работает офлайн (service worker не нужен, просто нет сетевых вызовов — тест через Playwright `route.abort`) |
| ROOM | authz-матрица (organizer/participant/anonymous × все эндпоинты); гонки: два `PUT /ballot` одновременно → последний побеждает, без 500; retention |
| SOLVER | таймаут → `FEASIBLE`; невыполнимость → объяснение; идемпотентность job; отмена job; worker-рестарт посреди задачи → задача не теряется (`attempts`) |
| DATA | contract-тест адаптера на demo и live; деградация при ошибке провайдера; `Provenance` в каждой схеме ответа; кэш с TTL и инвалидацией; ни один ключ не в бандле |
