# ADR-0004: Product profiles and single-language algorithms

- Status: Accepted
- Date: 2026-11-12

## Контекст
Продукты различаются тем, где считается алгоритм и есть ли общее состояние. Без явной классификации каждый
продукт изобретает свою архитектуру, а алгоритмы дублируются на TS и Python.

## Варианты
1. **Четыре профиля** (ARCHITECTURE_PLAN §3): CLIENT (TS в браузере, без БД), ROOM (Python, общее состояние
   комнаты, своя schema), SOLVER (Python + OR-Tools в worker, jobs), DATA (Python за адаптерами провайдеров,
   кэш + Provenance). Продукт может сочетать профили (P01 = DATA+ROOM).
2. Три «яруса» по месту вычисления — не различает «где считаем» и «есть ли общее состояние» (P15 требует общего
   состояния при простом алгоритме).
3. Всё на сервере — теряется офлайн-ценность CLIENT-продуктов (например, P20 обрабатывает файл локально).

## Решение
Вариант 1. Профиль записан в `registry.ts` (`profiles`) и определяет обязательный набор тестов
(TESTING_STRATEGY §9) и шаблон генератора. **Каждый алгоритм реализован ровно в одном языке**:
CLIENT — `products/<id>/web/src/algo/`, остальные — `python/algorithms/<domain>/` или `products/<id>/api/domain/`.

## Последствия
- Нет дублей TS/Python и расхождений результатов между ними.
- Смена профиля продукта (P24 CLIENT→DATA) — осознанное решение с записью в `DECISIONS.md` продукта.

## Как откатить
Добавление нового профиля — новый ADR; существующие продукты не меняются.
